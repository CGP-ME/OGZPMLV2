## Basis and boundary

The primary frame is not inferred from a strategy name. `ConfigLoader` resolves runtime key `broker.candleTimeframe` from existing `CANDLE_TIMEFRAME`, defaulting to `15m` (`foundation/ConfigLoader.js:962-985`); the committed PM2 app selects profile `paper` and sets `CANDLE_TIMEFRAME: '15m'` (`ecosystem.config.js:70-95`). The runner carries that value into both the orchestrator and MTF base frame (`run-empire-v2.js:621-632`). In this census, **non-primary** therefore means a bar whose stamped/source timeframe differs from that resolved value, not merely a component whose name contains “MTF.”

“Live” below means reachable from the production runner, not that a process was observed: this orb has no running PM2 process. “Defaults” means the committed `ecosystem.config.js` launch (`PROFILE=paper`, stocks/Alpaca, primary `15m`), corroborated by `launchProfiles.defaultProfile: paper` (`config/trading.config.json:20-21`).

Source classes:

- **Native bars**: the broker supplied that timeframe directly.
- **Primary-candle rollup**: code groups primary bars into a larger born timeframe. No such producer is wired to the runtime today.

## Explicit answers

### 1. Is `TimeframeEngine` instantiated anywhere?

**Not in the runtime.** Repository-wide production-code search finds no import or `new TimeframeEngine`. The only instance is the manual probe at `tools/probe-tfe-alive.js:76`; the implementation is otherwise self-contained at `core/TimeframeEngine.js:180-405`. Therefore the runner’s trace reason `tfe_owns_bar_production` (`run-empire-v2.js:973`) describes intended ownership, not a live owner.

### 2. Which strategies could take the confluence booster with config alone?

The booster is generic over emitted strategy results (`core/StrategyOrchestrator.js:1292-1303`), but config alone can enable it only where an existing strategy config already contains `confluenceBoost`. Intersecting those keys with registered strategies (`core/StrategyOrchestrator.js:1611-2208`) yields **13**:

`MADynamicSR`, `EMASMACrossover`, `LiquiditySweep`, `RSI`, `SmartMoneySweep`, `OpeningRangeBreakout`, `DonchianBreakout`, `OGZTPO`, `NoWickImbalance`, `PropSafeEMAPullback`, `EMATrendRetest`, `RSI2MeanReversion`, `TimeSeriesMomentum`.

All 13 are pipeline-enabled by committed paper config (`config/trading.config.json:260-277`) and all currently have `strategies.<name>.confluenceBoost={enabled:false,weight:0}` (`config/trading.config.json:1910-2257`). `VolumeProfile` has a similarly named config object but is not a registered strategy result; it is context boosting at `core/StrategyOrchestrator.js:2740-2759`, so config alone cannot make it a recipient of the MTF booster. `CandlePattern` and `BreakRetest` are registered but have no existing `confluenceBoost` key.

Config alone is **not sufficient to make any of the 13 actually receive a boost today**: the missing wire leaves only one ready frame, so no cross-frame score reaches the booster.

### 3. Derived-bar warm-up gap per timeframe

The adapter marks a frame ready at 30 delivered closed bars (`modules/MultiTimeframeAdapter.js:131,216-230`), while cross-frame availability needs two ready frames (paper `minReadyTimeframes=2`, `config/trading.config.json:247-258`). With committed primary 15m, `TimeframeEngine` can only derive equal/higher frames that are even multiples (`core/TimeframeEngine.js:102-120`). It emits a higher bar on the first base candle of the next bucket (`core/TimeframeEngine.js:329-354`), unless a watermark flush closes it (`core/TimeframeEngine.js:225-238`).

| Frame | Committed adapter status | 30 closed bars require | Transition-emission point from first aligned 15m source bar | Current gap |
|---|---|---:|---:|---|
| 1m | Filtered below 15m base | Not derivable | N/A | Native storage exists, but cannot enter this adapter. |
| 5m | Filtered below 15m base | Not derivable | N/A | Native storage exists, but cannot enter this adapter. |
| 15m | Active/base | 30 × 15m bars | Source bar 30 (7h30m of bars) | This one frame can warm; it is insufficient for 2-frame confluence. |
| 30m | Not in committed `orchestrator.mtfTimeframes` | 60 × 15m source bars | Source bar 61 (15h15m; or flush at 15h) | No producer and not selected. |
| 1h | Active | 120 × 15m source bars | Source bar 121 (30h15m; or flush at 30h) | No derived bars ever delivered; warm-up never starts. |
| 4h | Active | 480 × 15m source bars | Source bar 481 (120h15m; or flush at 120h) | No derived bars ever delivered; warm-up never starts. |
| 1d | Not in committed `orchestrator.mtfTimeframes` | 2,880 × 15m source bars | Source bar 2,881 (720h15m; or flush at 720h) | No producer and not selected. |

Elapsed values are ideal continuous UTC-bucket arithmetic, not equity-session wall time. Market closures/gaps increase wall-clock warm-up. The decisive current gap is not merely “wait longer”: without a `TimeframeEngine` instance/delivery wire, 1h and 4h remain at zero indefinitely.

### 4. MTF influences already firing on a live tick with committed defaults

With committed paper/stocks/Alpaca/15m defaults, the complete non-primary activity is:

1. **Alpaca emits native 1m bars despite the 15m request** (`brokers/AlpacaAdapter.js:683-696,1106`).
2. **Runner updates broker-liveness metadata and symbol last price from that 1m event, and stores it in native per-frame dashboard/TTP caches** (`run-empire-v2.js:930-944`). `StateManager.getEquity` marks each open trade from that symbol price (`core/StateManager.js:706-743`), so this 1m close can change mark-to-market equity and later equity-based risk/sizing; `getLastPrice` also supplies SessionRouter force-close pricing (`core/StateManager.js:892-919`). This is a real execution-state influence, not only display state.
3. **Runner then rejects that 1m bar from canonical trading analysis because 1m != active 15m** (`run-empire-v2.js:945-975`). It does not feed strategies, root MTF indicators, or the candle-close trading cycle.
4. **Dashboard consumers may display/read the native 1m cache** when dashboard transport is connected (`core/CandleProcessor.js:1208-1235`; historical requests can also fetch any native frame).

The complete list of **direct MTF-confluence effects on entry ranking, winner selection, strategy exit logic, or order permission is empty under committed defaults**. The native 1m last-price path above is the exception outside the confluence stack: it can indirectly affect later equity-based risk/position sizing and transition force-close pricing.

- MTF observation/booster and strategy-MTF call sites are enabled in paper, but receive only primary 15m canonical candles; one ready frame cannot satisfy `minReadyTimeframes=2`.
- Every per-strategy `confluenceBoost.enabled` is false and weight is zero.
- The only wired native non-primary order gate, TTP previous-1m-volume, is bypassed because paper’s top-level `venueGuards.ttp.enabled` is false.
- The adaptive selector cannot switch because its allowed list is hard-pinned to primary; committed Alpaca also emits no 5m event that would call `evaluate()`.

If a non-default profile selects crypto/Kraken, native non-primary ingestion/storage and the 5m selector evaluation also fire, but the trading fence and single-item allowed list still prevent those bars from changing the trading frame. If a profile with `venueGuards.ttp.enabled=true` is selected, the existing 1m TTP volume gate can block stock entries; neither condition is the committed default launch.
