**Executive Summary**  
The current OGZPMLV2 code‑base already contains a set of “engineered‑by‑AI” subsystems (Mercury bridge, read‑only toolbox, persistent LLM client, StateManager, receipt handling, etc.).  They are fragmented, have ad‑hoc guard‑rails (e.g. `mercury.ignore`) and are tightly coupled to a single LLM provider.  To meet the stated goals—correctness, auditability, determinism, architectural integrity, and long‑term maintainability—we must replace the ad‑hoc glue with a **modular, event‑sourced orchestration layer** that treats every repository mutation as a first‑class, verifiable event.  The design below shows the new runtime, the supporting verification and memory subsystems, and a concrete migration path.

## 3. Engineering Process Architecture  

1. **Intent Declaration** – a human writes a *process manifest* (YAML/JSON) describing the desired mutation (e.g., “add new risk‑check to `OrderExecutor`”).  
2. **Static Analysis** – the **Policy Engine** checks the manifest against contracts (ownership, config authority).  
3. **Task Generation** – the Orchestration Engine creates a *deterministic event* (`TaskCreated`) and queues it.  
4. **Agent Execution** – a **Claudito** runs the task using the **Tool Adapter** (searchRepo, openFile).  
5. **LLM Reasoning** – the **Verification Engine** (Mercury) receives the task, runs a ReAct loop, and returns a *structured response* with line citations.  
6. **Receipt Generation** – the response is stored as a **Receipt** (JSON) and committed to the `receipts/` directory.  
7. **Git Mutation** – the **Persistence Layer** applies the mutation **only** after the receipt passes a *policy‑gate* (e.g., “no ignored path”).  
8. **Replay & Auditing** – any past receipt can be replayed to reconstruct the exact repository state at any point.

All steps are **observable** (log entries) and **deterministic** (no hidden randomness; LLM temperature is forced to 0 for verification runs).

## 6. Memory Architecture  

* **Engineering Memory** – a *session‑aware* in‑memory cache of the current process manifest, recent receipts, and the latest RAG index.  
* **Long‑term Memory** – persisted as JSON receipts under `receipts/` and as Git commits.  
* **Cache Invalidation** – any new receipt triggers a background job that re‑indexes only the changed files (incremental RAG).

## 7. Receipt Architecture  

* **Schema** – `{ id, timestamp, author, taskManifest, llmResponse, citations, status }`.  
* **Signing** – each receipt is signed with the operator’s GPG key (ensures *attribution*).  
* **Storage** – `receipts/` directory, automatically committed with a *deterministic* commit message (`git commit -m "receipt: <id>"`).

## 10. Orchestration Architecture  

* **Event Store** – each task creates a JSON event (`TaskCreated`, `TaskStarted`, `TaskFinished`).  
* **Scheduler** – a lightweight Node.js worker pool (size configurable) that pulls from the event queue.  
* **Deterministic Replay** – the scheduler can be run with `--replay <event‑id>` to reconstruct exact state.  

---

## 11. Governance Architecture  

* **Human‑in‑the‑Loop** – the operator approves each receipt via a CLI (`ogz-meta/ask_1.js`) that displays the LLM response and required citations.  
* **Policy Engine** – runs before any Git mutation; rejects if any ignored path appears in the response (tests already enforce this).  
* **Audit Trail** – every receipt is signed, timestamped, and linked to the exact Git commit (`git rev‑parse HEAD`).

## 16. Expected Risks & Failure Modes  

| Risk | Mitigation |
|------|------------|
| **LLM Hallucination** – Mercury may fabricate citations. | Enforce `ensureNotIgnored` and `ensureWithinRepo` checks; reject any response containing a path not verified by the toolbox. |
| **Event Store Corruption** – JSON log could become inconsistent. | Store events in Git; each commit is signed and verified. |
| **Provider Outage** – Mercury‑2 downtime. | Fallback to OpenAI or Ollama via `PersistentLLMClient` (already provider‑agnostic). |
| **Policy Drift** – New code bypasses OPA checks. | CI step runs `opa eval` on every PR; block merge on failure. |
| **Performance Bottleneck** – Full‑repo RAG on every task. | Cache embeddings; only re‑index changed files (incremental). |
| **Tool‑Adapter Abuse** – Malicious tool call (e.g., `tailLog` on large files). | Enforce max‑bytes limits and path‑whitelisting in `ReadOnlyToolbox`. |

---

## 17. Strongest Criticisms of This Proposal  

* **Complexity Overhead** – Introducing Temporal and OPA adds operational surface; small teams may find it heavy.  
* **Dependency on External LLM** – Even with a fallback, the verification layer remains a single point of failure.  
* **Migration Cost** – Refactoring every existing script to emit events and receipts will be labor‑intensive.  
* **Potential Latency** – Full‑repo RAG for each verification may increase turnaround time; caching strategies must be robust.

### Final Answer  

If I inherited this ecosystem today, I would **retain** the proven, safety‑oriented components (`persistent_llm_client`, `ReadOnlyToolbox`, `StateManager`) and **replace** the ad‑hoc Mercury bridge, direct Git mutations, and scattered guard‑rails with a **deterministic, event‑sourced orchestration layer** backed by **Temporal**, **OPA**, and a **receipt‑driven audit trail**.  The migration proceeds in incremental, test‑driven phases, each backed by concrete code evidence (see citations).  This architecture eliminates architectural drift, hidden state, and silent mutations while keeping the system replaceable, auditable, and maintainable for the long term.
