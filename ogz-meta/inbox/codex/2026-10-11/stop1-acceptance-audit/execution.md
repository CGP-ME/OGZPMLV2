## Resolver, initialization, and call paths

`ConfigLoader` selects `PROFILE` or `launchProfiles.defaultProfile` (`foundation/ConfigLoader.js:447-457`), rejects unknown profiles (`488-506`), then constructs the bot snapshot. It copies profile-owned `sessionRouter`, `risk`, venue guards, and pipeline (`1067-1086`), copies base `execution`, `exits`, and `exitContracts` (`1097-1129`), and records source provenance. A file-backed descriptor can replace execution identity, route symbols/session, state/output roots, fee/tuning selection, and typed overrides (`903-1014`); this is an explicit override path, not a silent default. `PROFILE` and `BACKTEST_RUN_DESCRIPTOR_PATH` remain environment-controlled selector inputs.

The active runner resolves the snapshot before bot construction, then initializes: `RiskManager(buildRiskManagerConfig(resolvedConfig.config.risk, resolvedConfig.sources))` (`run-empire-v2.js:716-719`); broker adapters plus `OrderRouter` and `SessionRouter` (`900-934`); `OrderExecutor` (`1373-1405`); and `TradingLoop` (`1442-1464`). Session symbols originate from the resolved execution/session-router fields (`852-891`), rather than a raw broker default. Order execution therefore reaches configuration through the resolved snapshot and `ConfigLoader` reads, not direct `process.env` reads in these consumers.

## Runtime state is not configuration

`StateManager` initializes `isTrading: false` in fresh/empty state (`core/StateManager.js:546,634`) and writes it true only through its resume/start transitions (`2589,2659,2705,2757`). Malformed persisted `isTrading` is forced false with a pause reason (`4349-4352`). `OrderExecutor` rejects a non-backtest entry when that state is false (`2920-2923`); runner startup also reports the block (`run-empire-v2.js:1947-1948`). This is persisted mutable safety state, not a `settings.json` setting and not evidence that any running bot is paused or resumed.

## Static anomalies and unresolved acceptance evidence

This section supersedes the aggregate “covered” implication above. A key copied into a frozen policy is not thereby an active execution control.

1. **Confirmed in worktree and HEAD: percent take-profit is disconnected from the active exit coordinator.** `ExitContractManager` constructs `TakeProfitChecker` (`core/ExitContractManager.js:257-260`), but `checkExitConditions` calls stop loss, max hold, invalidation, channel trail, managed stop and `ProfitExitPlanner` (`364-424`), never `takeProfitChecker.check`. `TakeProfitChecker.check` is otherwise a class-local method (`core/exit/TakeProfitChecker.js:18-35`). Thus every configured `exitContracts.*.takeProfitPercent` is carried/validated and can affect TTP stock sizing through `OrderExecutor._entryProfitDistanceDecimal` (the follow-up's cited `2169-2182` path), but it is not proof of a percent target exit. This confirms follow-up item 29 rather than closing it.
2. **Confirmed in worktree and HEAD: percent trailing declarations are disconnected from an active percent trailing exit.** `TrailingStopChecker` alone reads `trailingStopPercent`/`trailingActivation` (`core/exit/TrailingStopChecker.js:54-72`), but it has no production instantiation/call. Active `ExitContractManager` dynamic trailing instead reads `frozenExitPolicy.profitManagement.trail` and ATR / `trailAtrMult` (`738-836`); it does not read contract `trailingStopPercent` or `trailingActivation`. These two values may still travel in strategy signal/contract data, but changing them does not establish a trailing-exit effect.
3. **Confirmed in worktree and HEAD: PatternBasedExitModel is tracking-only.** The runner constructs it and passes it to `OrderExecutor` (`run-empire-v2.js:737-742,1373-1405`); executor calls only `startTracking` and `stopTracking` (`core/OrderExecutor.js:4122-4129,4384-4391,5092-5094,5635-5638`). Repo search finds `evaluateExit` only at its definition (`core/PatternBasedExitModel.js:81`). Pattern-exit settings therefore do not produce an exit decision on this path.
4. **Confirmed in worktree and HEAD: `exitLogic.beScaleOut.feeBufferPercent` is policy-only.** It is normalized into frozen policy (`PolicyBuilder.js:280-287,598-604`) but `ProfitExitPlanner.planBeScaleOut` reads trigger type/fraction and never fee buffer (`core/ProfitExitPlanner.js:152-198`). The active break-even stop reads `exitLogic.trail.feeBufferPercent` instead (`ExitContractManager.js:839-872`).
5. **Confirmed in worktree and HEAD: `exitLogic.volatilityAdjustment.lookbackPeriods` is validated then discarded, while adjustment factors are hardcoded.** `PolicyBuilder.normalizeVolatilityAdjustment` requires a positive lookback at `297-302`, but returns `0.8` at low and `1.4` at high (`314-331`) without using it. The control therefore has no behavioral reader; the factors are replacement constants in source.
6. **Confirmed in worktree and HEAD: `fundTarget` has no entry/risk/exit consumer.** The runner creates `ModuleInitializer` (`run-empire-v2.js:639-640`) but no caller invokes its only `createTradingBrainConfig` factory; that factory is the core reader (`core/ModuleInitializer.js:24-35`). A dashboard/Discord notification module has a default parameter sourced from `fundTarget` (`utils/discordNotifier.js:405`), but no execution-path caller was found for that progress notification. It is a phantom execution control, not an active trading input.
7. **Field-level status for all 332 `exitContracts` leaves:** values fall into the following exact reader classes after strategy selection (`ExitContractManager.js:271-320`) and signal override (`971-1046`). `stopLossPercent` is active through `StopLossChecker` unless `stopType=structural`, which explicitly returns no percent stop (`StopLossChecker.js:40-68`). `maxHoldTimeMinutes` and `maxHoldMode` are active through `MaxHoldChecker` (`30-51`). `invalidationConditions`, `rsiExitLong`, `tsmLookback`, `tsmEntryTrailingReturn`, `trailType=channel`, and `trailChannelBars` have direct ECM paths (`377-396,459-617`). `partialExit.*` is active through `ProfitExitPlanner` (`152-198`). `minConfidence` and `atrMinPercent` are entry eligibility controls in `StrategyOrchestrator` (`637-649,2659-2662`). `trailAtrMult` is active only in dynamic ATR trailing (`760-765`). `maxConcurrentEntries`, `scaleIn.enabled`, `maxAdds`, `addTriggerClass`, `requireProfitConfirmation`, and `aggregateRiskCap` feed executor entry concurrency (`OrderExecutor.js:1610-1703`); `scaleIn.addSizingLadder` is cloned but has no executor reader, as follow-up item 28 records. `atrStopMult`, `targetRR`, `stopBufferPct`, `stopBufferAtr`, and strategy-specific geometry fields affect only strategies that explicitly read them to emit a contract hint (for example Donchian `modules/DonchianBreakout.js:84-119`, EMA retest `modules/EMATrendRetest.js:301-331`, PropSafe `modules/PropSafeEMAPullback.js:318-346`, NoWick `modules/NoWickImbalance.js:531-558`, and ORB `modules/OpeningRangeBreakout.js:459-500`); they do not create a generic contract target exit. `tpMode`/`tpAtrMultiple`, `takeProfitPercent`, `trailingStopPercent`, `trailingActivation`, `useStructuralExits`, and `_validated` are normalized/carried but have the disconnected or metadata-only limits identified above. `stopType=atr` does not itself convert a stop in `StopLossChecker`; it relies on a strategy having produced a percent stop. No claim is made that a strategy-specific producer ran.
8. **Confirmed in worktree and HEAD: the internal `dataFeed.volumeCapMaxReferenceAgeLimitMs` is a load-time validation ceiling only.** Loader injects it as `evalRules.ttp.volumeCap.maxReferenceAgeLimitMs` (`foundation/ConfigLoader.js:1230-1238`) and only the validation comparison reads it (`2040-2052`). No core/broker/runner behavior reader of that resolved field was found. It constrains whether a configuration can load; it does not govern evaluation after startup.
9. **Confirmed active in worktree and HEAD: `internals.broker.tradingIntervalMs` is not dead.** Loader renames it to `broker.tradingInterval` (`1240-1246`); runner uses it for failed-safe hold logging (`run-empire-v2.js:1854-1857`) and the open-position exit monitor timer (`2504-2515`).
10. **Correction: `proofPublication` is an active proof publisher configuration, not a phantom tree.** `ogz-meta/claudito-logger.js:376-392` reads all nine fields, and its publication path uses them at `643-646,654,734`. The active runner imports `TradingProofLogger` (`run-empire-v2.js:434`) and `OrderExecutor` imports it (`core/OrderExecutor.js:20`). This audit does not establish a successful publication, only a static producer/consumer path.
11. `node scripts/check-config-boundary.js` returns one scanner finding at `core/OrderExecutor.js:2382`. Manual source review classifies it as a **scanner false positive**: `this.ctx.backtestMode || this.ctx.paperTrading` is the ternary condition selecting configured slippage versus literal zero for live execution; it is not `ConfigLoader.get(...) || fallback`. The script therefore is not clean, but this finding does not establish a silent config override.
12. Loader and multiple consumers are dirty. The findings above are not acceptance of the clean commit and must be re-run against a staged/clean candidate before any shipping assertion.
13. Required runtime evidence remains absent by task restriction: resolved receipt (profile, descriptor, sources), state-file `isTrading` value, broker/session route, configuration fingerprint, live broker response, and entry/exit receipts.
